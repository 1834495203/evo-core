# EvoCore 架构实施路线

状态：核心主链路已完成统一（阶段 1–6 核心能力已接入 `evo_core` 与 `evo_core/system/`，并通过本地测试套件验证；真实长程科研基准与可选高级组件持续演进）。

目标架构见 [ARCHITECTURE.md](ARCHITECTURE.md)，模块边界与调用关系见 [MODULES.md](MODULES.md)。

## 阶段 1：统一执行边界和正式状态（已实现）

目的：先修正会使插件约束、预算和完成标记不可信的问题。

主要工作：

- 主 Agent 和子 Agent 共用模型/工具执行入口，统一钩子、事件和预算核算。
- 提供真正的工具执行前检查；明确允许、拒绝和延后执行的语义。
- 分开表示运行结束、未评审交付和科学结论；本地检查记录问题，不强制研究员返工。
- 为后续外部任务和用户指令预留控制边界。

验收：子 Agent 不绕过检查和预算；要求的前置检查失败时实验未被启动；报告缺失或验收未通过时不能标记验收成功。已有基本运行和插件关闭行为保持可用。

下一份细化文档：执行生命周期、状态转换、插件兼容方式与隔离验证方案。

## 阶段 2：统一研究记录并接入实验 Harness

目的：建立权威实验记录和可追溯的研究事实。

主要工作：

- 定义研究记录存储和实验提交/查询接口。
- 通过适配器复用 harness 的版本记录、冻结输入和原始产物归档。
- Agent 从实验结果创建带证据引用的观察和决定。
- 实验任务独立于主 Agent 生命周期，恢复先查询对账。

验收：从一条结论找到实验、代码快照、参数和原始结果；修复生成新实验而不覆盖旧结果；主 Agent 恢复后可接回已有任务。

## 阶段 3：打通单分支研究闭环

目的：在不依赖并行的情况下，完成可持续、可收尾的自主研究。

主要工作：

- 任务理解、文献定位、复现/基线、观察、实验、阶段决策和报告。
- 在方向变化、异常和停滞等节点持续核查文献。
- 保存复现目标与偏差，区分程序失败、科学负结果和证据不足。
- 维护计划与评价协议版本，为验证和报告预留预算。

验收：仅给任务即可形成完整证据链；假设被推翻也能交付；发现已有解法时能记录依据并调整方向；预算到达时停止扩张并给出诚实报告。

## 阶段 4：实时观察和只读问答

目的：用户可以随时知道研究在做什么，以及为什么。

主要工作：

- 从统一事件构建状态快照，支持断线后补取事件。
- 展示当前问题、运行实验、研究笔记、文献、产物、下一步和预算。
- 只读问答从快照和证据检索回答问题，带时间及依据。

验收：询问进度不阻塞主 Agent；界面和问答引用同一版本事实；正在运行、等待和失联状态不会混淆；界面重连可恢复记录。

## 阶段 5：运行中的用户指导

目的：让用户建议和约束变更可靠送达主研究。

主要工作：

- 持久消息队列，区分询问、建议、明确指令和运行控制。
- 记录接收、处理及应用结果，方向修改生成新计划版本。
- 在合适的执行边界应用变更；明确现有实验与后续调度的处理方式。

验收：改方向后新任务使用新计划；已运行实验不丢失；用户能看到指令何时生效；恢复后不会重复或漏处理指令。

## 阶段 6：资源约束下的并行实验

目的：在证据和状态可靠的基础上提高吞吐。

主要工作：

- 把单工作单扩展为可排队的任务集合，加入资源预约、心跳和执行尝试。
- 为实验提供独立源码快照、目录和输出。
- 统一结果提交与预算核算，支持独立实验的并行和结果汇总。
- 再按需要加入多研究分支及可插拔搜索策略。

验收：并行任务不互改代码和结果；资源限制生效；失败重试不重复登记成果；恢复不会无意重复提交已接受的任务。

## 阶段 7：研究质量与长期稳定性

目的：用实际任务验证系统能力，逐步改善上下文和研究策略。

主要工作：

- 建立复现、负面结果、理论限制、长实验、方向修改等代表性任务。
- 检查结论与图表的来源、协议变更和开发/独立验证的区别。
- 根据轨迹改进检索、分支记忆和阶段决策；长期经验与技能演化按需接入。

验收：不仅检查程序跑完，还检查证据引用、文献定位、负面结果保留、恢复、用户指导和预算收尾。对无法可靠完成的任务明确记录失败模式，不宣称已具备跨领域科研稳定性。

## 贯穿各阶段的约束

- 阶段 1 起持续保留回归验证；增加阶段能力时补充对应的行为验证。
- 保持内核小，实验 Harness 和可选科研策略通过接口衔接。
- 原始证据不随上下文压缩、报告修改或方向变化而丢失。
- 数据与事件通过统一提交入口修改；读端使用一致快照。
- 新版设计与现有研究运行隔离，后续实现不隐式迁移在跑任务。
- 先完成可验证的小闭环，再细化并行、复杂搜索及长期自进化。
